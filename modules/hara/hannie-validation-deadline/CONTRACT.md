## Non-executing client/consent adapter

src/client.mjs models one exact consent preview with the owner-approved risk text and two required explicit choices. recordConsentSelection produces only UNAUTHENTICATED_CONSENT_SELECTION / REQUIRES_OWNER_AUTHENTICATION. It is not a grant, signature, server approval or proof of a human action; client-supplied time/deadlines/digests must not be trusted as server authority. An admission service must independently authenticate the owner, fetch authoritative grant/context/policy/time and issue a separately bound approval. This adapter is not connected to execute().

presentResult structurally checks the exact supported receipt profile/version, request/context/event/snapshot binding, observation meanings and supported release point. It returns plain presentation strings; it performs no database/network access, fresh server authorization or cryptographic authenticity verification. It refuses legacy/unknown success profiles, incompatible receipt fields and payload attached to unknown/withheld/denied outcomes. No automatic retry is suggested. Missing historical time trust is not presented as something a fresh consent alone can recreate. Real browser rendering must use text-safe rendering, authentication and current server APIs; none is built here.

Thirteen separate client controls include an actual synthetic worker receipt; mutated receipt cases are local decoder controls, not browser or identity integration. The runtime suite remains independently counted. Restore/trust-epoch, authenticated admission and a real consent UI remain OPEN.

A withheld-outcome view additionally requires the exact profile/operation binding and a positive safe-integer auditSequence. Missing, zero, fractional or string audit sequences are protocol errors; they cannot be presented as a confirmed committed outcome. This is structural validation only, not an authenticity check.

## Admission snapshot conformance model

src/admission.mjs is a pure synthetic host-snapshot checker, not an authentication provider, grant issuer, approval writer or admission endpoint. Its only positive outcome is SNAPSHOT_REQUIREMENTS_SATISFIED with authorityGranted=false; it never returns a usable approval. All input verification flags are assertions in a test snapshot, not evidence that real credentials/origin/time were verified. Production use cannot infer authority from those flags.

The model checks actor owner/tenant/session, verified-origin assertion, policy/profile, current write ACL, exact active grant/generation/opt-in, server snapshot time against both expiries, an open unexpired challenge bound to request/context/preview, two explicit owner-confirmation choices and exact selection binding. Client selectedAt cannot override expired server-snapshot time. It accepts only SYNTHETIC_ADMISSION_SNAPSHOT_V1 and is not connected to execute(). Real credential verification, authoritative snapshot acquisition, challenge consumption, durable idempotent approval issuance and revoke-race handling at issuance are not implemented by this model. Runtime still independently rechecks expiry/grant/approval before mutation.

Twenty snapshot controls run separately from the 24 runtime and 13 client controls, with before/after fixture-state equality for positive and negative checks. A consumed-challenge input is rejected; this is not proof of concurrent challenge consumption. Full restore/trust-epoch remains OPEN.

## Stateful synthetic approval-issuance fixture

The test-only modules tests/approval-store.mjs and tests/approval-store-worker.mjs add a separate durable fixture challenge and exact approval flow. They are not exported by src/index.mjs or served as an endpoint. The supervisor rejects non-fixture paths (only a canonical calendar.sqlite immediately under a hara-vd-* directory under the OS temp root) and actors other than the fixed synthetic-owner/tenant/session. This is test-fixture authority, not genuine authentication; direct local database access is outside this fixture threat model.

An open challenge binds context/request/preview/expiry and exact approval ID. The fixture loads current calendar/grant from SQLite, checks synthetic snapshot requirements, then consumes one open challenge and inserts one exact fixture approval in a single BEGIN IMMEDIATE transaction. Same-identity replay reconstructs existing state and cannot reset a runtime-consumed approval. The approval is an owner-consent fixture, not TACP or an agenda effect: the real candidate mutation still has its own final grant/approval/expiry checks and atomic decision/effect commit.

Writers use the same private-path Linux flock as the candidate and are killed with SIGKILL before, within a native WAL write, or after COMMIT. The supervisor ignores positive ACKs and opens a separate read-only process to reconstruct challenge/approval binding. Missing or contradictory durable rows give UNKNOWN; no repair or second write. Each successful fixture readback explicitly reports realAuthorityGranted=false. Approval persistence after expiry is not claimed to be usable: readback reports expiry, and execution independently denies expired permission. No absolute issuance-storage deadline is promised.

Sixteen separate stateful fixture controls cover before/after-commit crash, false/lost ACK, actual concurrent confirmations, scope/expiry/revoke/generation/opt-in rejection, read-only recovery and replay after runtime consumption. They do not test a real identity provider, browser-origin verification, official approval issuer, external time or restore/trust-epoch. Those production gates remain open.

A native approval-WAL stall may leave a historically reconstructed but expired fixture approval. This is not a timely or usable approval: the expiry is reported and the runtime denies the subsequent mutation without an effect. The fixture does not claim a hard issuance-storage deadline.
